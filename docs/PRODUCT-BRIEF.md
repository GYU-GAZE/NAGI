# nAGI Extension

You are responsible for designing and implementing a browser extension called **nAGI**.

Treat this as a real software project, not a visual prototype.

The extension exists to turn the standard ChatGPT web interface into a highly customizable, modular and more practical client layer while still using the official ChatGPT website underneath.

The user should continue using their normal ChatGPT account, chats, Projects, models, tools, memory and subscription.

nAGI must NOT become a separate ChatGPT client using the OpenAI API.

The core idea is:

> ChatGPT remains the backend and canonical conversation system.
> nAGI becomes a configurable interface, organization and quality-of-life layer on top of it.

The project must prioritize actual utility and performance instead of becoming merely a theme extension.

---

# 1. PRODUCT GOALS

nAGI should eventually provide five major systems:

1. Appearance customization
2. Modular navigation/layout
3. Personas
4. Conversation Chains
5. ChatGPT quality-of-life and performance improvements

All major systems must be optional.

A user must be able to install nAGI and use only the performance features, only the theme engine, only personas, or the complete interface.

Do not force the full nAGI experience.

---

# 2. IMPORTANT ARCHITECTURAL RULE

Do not rebuild ChatGPT from scratch.

Do not create a new chat backend.

Do not use the OpenAI API for normal conversation.

Do not extract authentication/session tokens.

Do not depend on private ChatGPT backend endpoints unless absolutely unavoidable and explicitly approved by the user.

Prefer interacting with the existing ChatGPT frontend and DOM.

The extension should act as a modular layer above `chatgpt.com`.

The implementation should be resilient to ChatGPT frontend changes whenever realistically possible.

Avoid fragile selectors such as deeply nested autogenerated Tailwind/class chains.

Build abstraction/adapters around ChatGPT DOM integration.

For example:

```text
ChatGPTAdapter
├─ getCurrentConversation()
├─ getCurrentProject()
├─ observeGenerationState()
├─ sendMessage()
├─ createProjectChat()
├─ inspectConversationLimit()
└─ etc.

```

If ChatGPT changes internally, ideally only this adapter should require significant repairs.

---

# 3. BROWSER SUPPORT

Design using the WebExtensions model.

Manifest V3 compatibility is desirable.

Primary concern is desktop browsers.

Try to keep the architecture portable between Chromium and Firefox whenever possible instead of hardcoding Chrome-only assumptions.

If a feature cannot reasonably support both initially, document the limitation instead of creating a complicated compatibility layer prematurely.

---

# 4. PRIVACY

nAGI should be local-first.

By default:

- no external server
- no analytics
- no telemetry
- no conversation uploads
- no avatar uploads to third parties
- no external database

Store extension configuration locally using browser extension storage / IndexedDB as appropriate.

Assume chats may contain private information.

Do not introduce remote infrastructure unless the user explicitly requests it later.



HTML + CSS customization is enough initially and is safer.

# 8. PERSONAS

nAGI should introduce a Persona system.

A Persona represents the assistant identity currently answering.

Each Persona should contain at least:

```text
Persona
├─ id
├─ name
├─ custom instructions
├─ avatar configuration
├─ idle appearance
├─ thinking appearance
└─ talking appearance

```

Example personas:

```text

Academic Assistant
Editor

```

The persona name can be displayed beside assistant responses.

Displaying Persona names and avatars must both be optional.

# 10. PERSONA STATES

A Persona has three primary visual states:

## IDLE

The assistant is not currently generating.

The previous response is complete and the interface is waiting for user input.

## THINKING

A response has begun but final answer text is not currently streaming.

This can include:

- reasoning/progress status
- searches
- tool use
- file reading
- GitHub access
- other activity shown by ChatGPT

## TALKING

Final assistant answer text is actively streaming into the page.

The state machine may therefore look like:

```text
idle
→ thinking
→ talking
→ thinking
→ talking
→ idle

```

Do not assume generation consists of exactly one thinking phase followed by exactly one talking phase.

# 12. ANSWER WITH...

The active Persona for a conversation is controlled through a feature called:

**Answer with...**

Example:

```text
Answer with...

[nAGI avatar] nAGI

```

or:

```text
[GM avatar] Isekai GM

```

This controls both:

- visual assistant identity
- the Persona's Custom Instructions

Do NOT switch the global ChatGPT Custom Instructions merely because a browser tab receives focus.

That creates cross-tab race conditions.

Instead, treat Persona activation as an atomic SEND transaction.

When the user presses Send:

```text
1. intercept the send action
2. inspect the current tab's Answer with Persona
3. acquire a global extension Persona lock
4. verify the required ChatGPT Custom Instructions
5. change them if necessary
6. verify that the correct instructions are active
7. only then allow the original message to send
8. keep the Persona lock while the answer is generating
9. release the lock after generation completes

```

This behavior is important.

Example:

```text
TAB A
Answer with: Isekai GM

TAB B
Answer with: nAGI

```

If TAB A is currently generating as Isekai GM and the user tries to send from TAB B:

```text
Another Persona is currently active:
Isekai GM

[Send when available]
[Cancel]

```

A force-switch option may exist later but must NOT be the default.

Default behavior should prioritize avoiding accidental Persona contamination.

# 13. CUSTOM INSTRUCTIONS

A central requirement is the ability for Personas to provide actual ChatGPT Custom Instructions.

This is necessary because some use cases depend on removing the normal global personality entirely.

Example:

The normal nAGI Persona may intentionally use highly informal language and unusual punctuation.

An RPG GM Persona may require formal prose and correct punctuation.

Simply injecting another message into conversation context is not considered sufficient if the existing global instructions continue influencing responses.

Therefore nAGI should be capable of switching the actual ChatGPT Custom Instructions used by the account when a Persona requires it.

Important:

There is currently no public Custom Instructions API.

Treat this integration as a fragile adapter that may require interaction with the visible ChatGPT settings UI.

Do NOT use undocumented private authentication endpoints or steal session credentials.

Before overwriting instructions:

```text
read current value
→ store backup locally
→ write Persona instructions
→ verify successful save
→ mark Persona active

```

Always include a recovery mechanism:

```text
Restore original ChatGPT instructions

```

Never risk permanently destroying the user's previous Custom Instructions.

Version Persona instructions locally.

Example:

```text
nAGI
v1
v2
v3

Isekai GM
v1
v2
v3

```

Sessions may record which Persona version was active when they were created.

# 14. CONVERSATION CHAINS

A major nAGI feature is **Conversation Chains**.

ChatGPT has a maximum length for individual conversations.

Users often need to continue work in a new chat.

From the user's perspective this should feel like continuing the same logical conversation.

A Chain is a local nAGI structure connecting multiple real ChatGPT conversations.

Example:

```text
Isekai Slop
Main Campaign

Session 01
Session 02
Session 03
Session 04
Session 05 ← current

```

To ChatGPT these remain five separate chats.

To nAGI they form one logical conversation.

---

# 15. CHAINS ARE NOT PROJECTS

This distinction is critical.

A ChatGPT Project may contain:

```text
main campaign chats
prompt development
off-topic discussion
novel planning
tests
research

```

Therefore:

```text
Project ≠ Chain

```

One Project can contain multiple Chains.

Example:

```text
PROJECT: Isekai Slop

CHAINS

Main Campaign
Prompt Development
Webnovel Planning
Experimental Runs

UNASSIGNED CHATS

random prompt discussion
cover discussion
test conversation

```

Users must be able to:

- create multiple Chains in one Project
- manually add chats to Chains
- remove chats from Chains
- reorder chats
- mark a current chat
- rename Chains
- navigate previous/next Chain session
- keep chats unassigned
- optionally allow one chat to belong to multiple Chains later

Do not automatically guess the semantic role of every chat.

Explicit user organization is preferable to unreliable AI categorization.

---

# 16. MANUAL CHAIN ORDER

Chain order must not depend exclusively on creation date.

Users must be able to drag/reorder conversations manually.

Example:

```text
01 Session A
02 Session C
03 Session B

```

can be rearranged later.

Store Chain ordering as nAGI metadata.

---

# 17. CHAIN PERSONA MEMORY

Each Chain should store Persona settings.

Example:

```text
Main Campaign

default persona: Isekai GM
remember last used persona: yes
last persona: Isekai GM

```

When reopening that Chain:

```text
Answer with: Isekai GM

```

should already be selected.

Another Chain in the same Project could use nAGI instead.

Example:

```text
Isekai Slop
├ Main Campaign       → Isekai GM
├ Prompt Development  → nAGI
└ Webnovel Planning   → Editor

```

---

# 18. CHAIN CONTINUATION

Users must be able to manually create a fresh continuation even before a conversation reaches its maximum length.

This is needed when:

- Project Instructions changed
- Persona prompt changed
- they want a fresh context
- they are testing a new GM version

Provide something conceptually equivalent to:

```text
Continue in new chat

```

For certain Chains this should:

```text
create new conversation
→ inside the same ChatGPT Project
→ append it to current Chain
→ mark as current
→ select the Chain's Persona
→ optionally send a configured continuation message

```

For the Isekai Slop example that configured continuation message is:

```text
[RESUME]

```

Do not hardcode `[RESUME]`.

Each Chain should have configurable continuation behavior.

---

# 19. AUTOMATIC ROLLOVER

nAGI should detect when ChatGPT reports that the maximum conversation length has been reached.

For Chains with Auto Rollover enabled:

```text
conversation limit detected
→ identify current Project
→ create a new chat in the same Project
→ add it to the same Chain
→ increment session number
→ select correct Persona
→ send configured continuation message if present
→ mark new session current

```

User-facing result could look like:

```text
Conversation limit reached
Main Campaign 13 → 14
Continuation ready

```

The user should not have to manually navigate back into the Project and create another chat.

# 21. ACTIVITY LOG

ChatGPT often displays useful intermediate progress text while generating:

```text
reading file...
checking game state...
searching...
considering route...

```

Sometimes those visible frontend messages later disappear or are replaced by a shorter summary.

nAGI should try to preserve progress information that was ACTUALLY SHOWN to the browser.

Use a MutationObserver or equivalent observation strategy.

Example:

```text
23:47:13 THINK checking current scene
23:47:15 FILE economy.md
23:47:18 FILE Mira.json
23:47:21 THINK reconciling route
23:47:23 TOOL GitHub
23:47:27 TALK response started

```

Important:

This is NOT an attempt to obtain private model chain-of-thought.

Do not attempt to expose hidden reasoning that ChatGPT never sent to the frontend.

Only preserve visible activity/progress information that the web UI actually received.

Call this feature:

**Activity Log**

not "raw chain of thought".

# 22. PERFORMANCE

Performance is a first-class product feature.

Long ChatGPT conversations can make the web frontend progressively slower.

Symptoms include:

- slow rendering
- delayed progress updates
- thinking/tool status visually freezing while backend work continues
- the page only appearing up to date after reload
- large DOM trees
- expensive React updates

Research and borrow proven ideas from existing approaches such as:

- conversation virtualization
- unloading old turns
- CSS containment
- `content-visibility`
- reduced animations
- reducing unnecessary DOM work

Possible user setting:

```text
Conversation optimization

Automatic
CSS containment only
Aggressive virtualization
Off

```

Possible setting:

```text
Keep nearby turns:
30

```

Avoid breaking:

- Ctrl+F where possible
- text selection
- copying
- tool widgets
- current streaming response
- conversation navigation

Performance improvements should be benchmarked rather than assumed.

# 26. ENGINEERING QUALITY

This project will interact with a frequently changing web application.

Therefore:

- isolate DOM selectors
- document assumptions
- avoid magic constants
- keep selectors/adapters testable
- log integration failures clearly
- never silently corrupt settings
- provide graceful fallbacks
- make feature detection preferable to strict DOM assumptions
- use TypeScript unless there is a compelling reason not to
- keep modules loosely coupled
- create clear interfaces between DOM adapters and nAGI business logic

Do not build a huge monolithic `content.js`.

# 28. FAILURE SAFETY

Particular care is required around Custom Instructions.

If switching Persona fails:

DO NOT send the user's prompt under an uncertain Persona silently.

Prefer:

```text
Could not activate Persona "Isekai GM".
Message was not sent.

[Retry]
[Send without Persona]

```

Never silently use the wrong Persona.

Likewise, if automatic rollover cannot determine the Project safely:

do not create a random chat outside the Project and pretend everything succeeded.

Explain the integration failure.

# 34. WORKING STYLE

You are allowed to inspect the live ChatGPT frontend, test selectors, prototype approaches and revise architecture as necessary.

Do not blindly implement assumptions from this document if the real frontend proves them wrong.

When an integration depends on current ChatGPT behavior:

1. inspect how it currently works
2. document the finding
3. isolate that behavior behind an adapter
4. implement it defensively

Do not repeatedly ask the user for minor implementation choices.

Choose reasonable technical defaults and document them.

Ask only when a decision would substantially change the product direction or create a meaningful security/privacy tradeoff.

If a requested behavior turns out to be technically impossible or dangerously fragile, explain precisely why and propose the closest architecture that preserves the original intention.

---

# 35. DO NOT DO THESE THINGS

Do not:

- turn this into an OpenAI API client
- require API keys
- extract ChatGPT auth tokens
- expose hidden private chain-of-thought
- upload conversations externally
- silently modify Custom Instructions
- silently use the wrong Persona
- assume Project = Chain
- hardcode `[RESUME]`
- force avatars
- force the nAGI theme
- depend on a single giant DOM selector
- rewrite the complete ChatGPT frontend before the architecture is proven
- optimize only appearance while ignoring QoL/performance

# 36. PRODUCT DEFINITION

The target is not:

> "ChatGPT but prettier."

The target is:

> a modular enhancement layer for ChatGPT Web that lets users control interface, identities, conversation organization and performance while keeping the official ChatGPT service underneath.

Its usefulness should remain obvious even to someone who disables every cosmetic feature.
